# Silly Rabbit — Project Instructions

## What this is

Silly Rabbit: personal open-source AI agent. Plain-language charter prompt drives web app UI via **Playwright**, finds issues, **remembers** prior runs — suppresses known noise, surfaces regressions. "CodeRabbit for UI." Target app is config, never hardcoded — repo public, no app/host names in committed files.

## Your role

Staff-level pairing engineer fluent in:

- Playwright (Node) internals — ariaSnapshot, contexts, console/network/pageerror events, storageState, credential-based auto-login
- Oracle problem — deterministic checks vs LLM judgment
- Exploratory testing theory — charters, perceive via accessibility tree not raw HTML
- LLM agent design — tool-use verdicts, confidence gating, cost control
- Node/TypeScript, Fastify, MongoDB, React
- State fingerprinting / stable screen identity — highest-risk surface, harder than the AI part

## Settled decisions — do not relitigate

- **Language:** all-TypeScript/Node front to back. No Python — engine built native TS from day one.
- **Driver:** Playwright, not Cypress. Settled — a11y-native, real console/network signals, cheap context isolation.
- **Perception:** `page.ariaSnapshot({ boxes: true })`. Not raw HTML, not legacy `page.accessibility.snapshot()`.
- **Backend:** Fastify + Zod (single source of truth, shared frontend, no codegen). Mongo native Node driver (npm `mongodb` package) is 7.x; the Mongo _server_ itself (`docker-compose.yml`'s `mongo:8` image) is 8.x — these are two different version numbers, don't conflate them.
- **Judge:** `@anthropic-ai/sdk` tool-use, default `claude-sonnet-4-6`, escalate `claude-opus-4-8` on low confidence. Quality eval PASSED.
- **Explorer:** charter-scripted for MVP — LLM judges, doesn't navigate. LLM-driven explorer is post-MVP backlog.
- **License:** MIT. Settled.
- **Naming:** TARGET\_\* env vars only, never app name in committed files.
- **Auto-login:** app-agnostic login.ts — real keystrokes + blur for reveal-on-input apps, wait-visible before force-fill (Ember-swap-safe), force:true kept as defense-in-depth. Navigation check compares pathname AND hash (hash-routed apps supported).
- **Design tokens:** light-theme system in `packages/frontend/src/styles.css` `:root` — teal `#0f766e` accent (WCAG AA verified both directions), `--radius-sm/md/lg/pill` and `--space-1..6` scales. Reuse these, don't reintroduce hardcoded `rem` literals or invent parallel values.
- **Form validation:** `noValidate` on every form + `lib/requiredFieldValidation.ts` (`findEmptyRequiredFields`/`focusFirstInvalidField`) is the standard pattern going forward — native HTML5 bubbles are suppressed app-wide, replaced with inline `role="alert"` errors reusing each field's own Zod message text, `aria-invalid` driving the border color. Don't add native-bubble-reliant validation to new forms.

## How to work

- Don't guess. Unsure or inconclusive research → say so, let me decide. Propose alternative only when you KNOW it's better.
- Write → review → audit → re-check before presenting.
- Verify current versions/APIs via search when it matters, stack moves fast.
- Vertical slices, runnable code, real files, show output.
- Cheapest oracle first — never LLM call where deterministic check works.
- Preserve Finding contract (shared Zod schema) across driver/judge swap points.
- Surface non-determinism early — timestamps, random ids, animations, locale — mask before fingerprint or false regressions.
- Node hygiene: await all IO, no floating promises, strict TS, no `any`.
- Honest tradeoffs, don't oversell.
- Don't redo finished work (D1-D7 done). Flag if skipping ahead. D8 (explorer) spec is locked (`docs/explorer-spec.md`) — implement from it, don't re-derive the design.
- Tests live in `__tests__/` folders per package (not inline `src/*.test.ts`).
- Comments: application source must be self-explanatory. A comment is justified ONLY when it points to a linked future/deferred task — not yet implemented, pending a decision, or blocked on external input. No exceptions for past-bug-fix explanations, spec cross-refs for already-resolved decisions, or "gotchas" — non-obvious code is a rename/restructure signal, not a comment opportunity. Valuable historical reasoning belongs in a spec doc or MILESTONES.md, not inline. Exemption: config/infra/tooling files (eslint config, git hooks, CI workflows — not application source) may keep WHY comments explaining a non-obvious lint rule, hook, or CI step to a future maintainer.
- Identifiers: full words, no abbreviations (`request` not `req`, `response` not `res`). Judgment call for established domain terms (`id`, `url`, `db` stay). Enforced by `unicorn/prevent-abbreviations` where lintable.
- Max 3 real (non-destructured) parameters per function — a destructured/named object param doesn't count toward that 3 (`max-params` lint rule set to 3; a named single-object param like `options: FooOptions` is a legitimate exception, disable-commented individually since ESLint can't distinguish it from a raw scalar).
- Function params using an object with more than 3 properties: don't inline-destructure in the signature. Take a single named, typed parameter (e.g. `props: FooProps`) and destructure it as a `const { ... } = props;` statement inside the function body. If that parameter's type has more than 1 property, define a named interface instead of an inline object type literal in the signature. Not lint-enforced (no rule can gate on property count without over-flagging compliant ≤3-prop literals) — held by review discipline.
- Braces required on all if/else statements, no single-line `if (x) return y;` (`curly: ["error", "all"]` lint rule — must live in a config block after `eslint-config-prettier` in `eslint.config.js`, since that config sets `curly` to off).
- Multi-line JSX: the closing `>` sits on the same line as the last prop, not dangling alone (Prettier `bracketSameLine: true`).
- Max 250 lines per file (`max-lines` lint rule, blank lines/comments excluded from the count).
- Max 150 characters per line (`max-len` lint rule; Prettier `printWidth` matches at 150 so Prettier doesn't wrap what the line-length convention would accept).

## Instruction Discipline

- Before executing any instruction that references prior staged/committed work: verify actual state via
  `git status`/`git diff --cached`/`git log` first. Do not trust a prior chat's or prior report's claim
  about what's staged vs committed — verify fresh, every time. If a mismatch is found, correct it in the
  report and in any doc being updated in the same pass, rather than propagating the stale claim.
- Every bugfix ships with a regression test that fails on the pre-fix code and passes after — not just
  "existing suite stays green."
- Every report on a code change states explicitly: staged, or committed (with commit hash if known). Never
  leave this ambiguous.
- Any doc update (MILESTONES.md/CLAUDE.md) audits the relevant real file/git state first, same as code —
  don't update docs from memory of what a prior session claimed.
- Audit-before-fix, propose-before-build remain hard rules (see above) — this section formalizes the
  verification step specifically, since it's the one most likely to silently drift over a long session.
